Veredito por dentro

Um pull request entra. Seis promotores acusam, um advogado testa cada acusação com ferramenta de verdade, e um juiz determinístico sentencia. Sai um parecer em que cada linha aponta para um artefato que outra pessoa consegue rodar — e o que não foi provado aparece nomeado, nunca em silêncio.

Como ler este documento

Ele acompanha uma rodada do começo ao fim, na ordem em que o código executa. Cada etapa traz o que roda (as funções, com arquivo), o que entra e o que sai, o que fica gravado em disco e por que aquela peça existe — quase toda decisão aqui foi comprada por um erro real, e sem o motivo a regra parece arbitrária.

A ideia em uma frase

Revisor de código que trata cada suspeita como acusação: nada vira parecer sem prova reproduzível. O modelo caro nunca decide sozinho — ele produz um artefato, e quem decide se aquilo provou alguma coisa é código determinístico que um humano consegue ler.

A regra central

Veredito + confiança + evidência. A severidade acompanha a força da prova, não a gravidade teórica. E nada é descartado em silêncio.

Os três estados, e por que o terceiro é obrigatório

Todo desfecho cai em um de três baldes. O terceiro é o que impede o produto de mentir quando a infraestrutura falha.

EstadoSignificaVai para
PROVADO Existe artefato: um teste que passa no código de hoje e quebra com a mudança, ou chamadas HTTP contra o app rodando. Condenados
REFUTADO Foi testado, o teste rodou, a acusação não se sustentou. É um resultado forte. Descartados, com motivo
INCONCLUSIVO Timeout, parse quebrado, ferramenta que falhou, recusa do classificador, LLM do app alvo dublê. Ausência de observação não é refutação. Inconclusivos, com a causa
O erro que o produto existe para impedir

Num veredito binário, "não consegui provar" vira absolvição limpa — e a categoria carro-chefe se esvazia sozinha parecendo rigor. Somar inconclusivos com refutados e anunciar "refutou tudo" quando nenhuma ferramenta funcionou é absolvição falsa. Já foi cometido duas vezes nos relatórios do próprio projeto, e é por isso que hoje isso é código com teste, não disciplina.

MAPA

O pipeline em uma tela

Um orquestrador e três tipos de chamada. Repare onde o dinheiro é gasto: seis chamadas baratas geram hipóteses, um funil corta, e só então o modelo caro entra — uma acusação por vez, isolado, com ferramenta na mão.

O esqueleto, em pseudocódigo

# veredito/orquestrador.py :: roda()
pre_voo()                          # senão a rodada nem começa

acusacoes = []
para cada lente em [injection, vazamento, prd, correcao, padroes, performance]:
    acusacoes += chamada_de_modelo(diff + contexto + orçamento, lente)   # Haiku

acusacoes = cruza(acusacoes, scanner_gratis(diff))    # bandit/semgrep EM PARALELO

veredictos = []
para cada acusacao em seleciona(acusacoes, TOP_N, COTAS, MAX_POR_LOCAL):
    veredictos.append( advogado(acusacao) )           # ← o laço caro, Opus

prova_as_fusoes(veredictos)                           # container, zero de API → fusao.json
parecer = juiz(veredictos)                            # regras determinísticas + formato

A síntese em linguagem natural do parecer ainda não existe — o que está no ar é determinístico e roda em milissegundos, sem rede.

ETAPA 00

Entrada: virar um endereço em dois commits

A maquinaria toda sabe trabalhar com (repositório local, commit base, commit head). A entrada é a porta que produz esses três a partir de um link de PR.

Três portas

revisa_pr.py

py -3.12 revisa_pr.py <url do PR> [--top-n N] [--so-preparar]

A porta da frente. Resolve o PR, monta os worktrees e sobe o orquestrador apontado para eles.

python -m veredito.orquestrador

--manual · --top-n N · --reusar · --sem-scanner

Roda contra um repositório já em disco, usando os ramos declarados em PR_BRANCH e BASE_BRANCH.

GitHub Action

.github/workflows/veredito.yml

Dispara em pull_request ou à mão. Chama revisa_pr.py e depois posta_parecer.py.

roda_bancada.py

a bancada de medição interna

Aponta o produto para um segundo projeto com defeitos plantados — é como se mede se o motor ainda funciona.

O que acontece dentro

  1. Resolve o endereço. Regex do PR, chamada à API do GitHub, título, adições, remoções, arquivos. veredito/entrada.py :: resolve() · partes() · commits_do_pr()
  2. Descobre o base certo. pulls/{n} devolve o topo do ramo de destino agora. Se a main andou desde a abertura do PR, esse commit carrega mudanças que não são do PR — e a prova diferencial passaria a medir o PR somado ao que entrou depois. O commit certo é o merge_base_commit, do endpoint compare. uma chamada a mais, e é a diferença entre provar o PR e provar outra coisa junto
  3. Clona raso. git init + fetch dos dois commits, em .repos/<dono>_<repo>. Não traz o repositório inteiro. veredito/entrada.py :: _garante_clone() · busca_os_dois()
  4. Monta os worktrees. Duas árvores de trabalho lado a lado, base/ e head/, fora dos repositórios. veredito/ferramentas.py :: monta_os_dois() · _garante_worktree()
  5. Exporta o ambiente e chama o orquestrador em subprocesso. revisa_pr.py :: main()
Ordem que não é opcional

O config resolve o projeto inteiro na importação: contas, rota de login, banco, layout dos testes — tudo sai do ambiente no instante em que o módulo carrega. Por isso duas coisas acontecem antes de qualquer import: o ambiente é atualizado, e os worktrees são criados.

Já mordeu duas vezes. Trocar o alvo depois da importação deixa metade da configuração apontando para o projeto anterior — uma rodada revisando um repositório e conversando com o app de outro, com o pré-voo dizendo verde. E quando os worktrees nasciam sob demanda, o veredito.yml do projeto (que é lido do worktree do base) ainda não existia: a rodada revisou um projeto que se descreve inteiro como se ele fosse mudo.

O que esperar de um PR de terceiro. Sem veredito.yml na raiz do repositório revisado, o advogado tem read_file e grep, e mais nada: sem app no ar não há http_request, sem compose declarado não há prova_diferencial. O parecer sai com refutação fundamentada e severidade no máximo MEDIA — a regra R2 rebaixa o que não é prova ponta a ponta. Isso é dito antes de gastar, não descoberto no fim.

ETAPA 01

Pré-voo: descobrir a rodada condenada antes de pagar por ela

Segundos, uma vez, antes de gastar cerca de US$0,07 por acusação. Nasceu de um dia em que a worktree estava corrompida e o advogado devolveu PROVADO com todas as chamadas falhando — infraestrutura podre virando veredito positivo. O juiz pega isso depois (regra R3b); o pré-voo pega antes.

Por que "o app serve o head" é fatal e não um aviso

Se o container estiver servindo o commit base, o http_request exercita código que não é o do PR — e o defeito simplesmente não existe de fora. Não é degradação: é medir a coisa errada achando que se está medindo a certa, e o parecer sai limpo e mentiroso. Custou uma rodada inteira.

O app de pé, e as duas regras que protegem quem roda

Se o projeto declara subir: true, o orquestrador levanta o app antes de tudo, dentro de um context manager que envolve a rodada inteira (subida.app_no_ar()). Duas regras:

  • Não derruba o que não subiu. App de pé é do operador — talvez com o navegador aberto nele.
  • O preparar (o seed) só roda se nós levantamos os containers. Seed reseta banco; rodá-lo num app que já servia apagaria dado que não é nosso.

Consequência: subir: true num app já no ar é no-op completo, verificado com zero comandos ao Docker. É isso que torna a opção segura de deixar ligada.

O prefixo que vai ser cacheado

Ainda no pré-voo, duas coisas são montadas uma vez por rodada porque são o prefixo compartilhado por todas as chamadas seguintes:

  • advogado.diff_do_pr() — o git diff base..head. Nunca é impresso: o time não pode ver o diff antes do agente trabalhar.
  • advogado.contexto_dos_arquivos(diff) — o conteúdo integral dos arquivos que o PR toca, para o advogado não gastar volta lendo o que já poderia ter.
Cache de prompt

O Opus 5 cacheia a partir de 512 tokens e a leitura custa ~10%. Como o diff é o mesmo prefixo em toda chamada, ele entra antes da acusação, e o cache_control marca o fim do trecho compartilhado. cache_read igual a zero na primeira acusação é sinal de que algo varia no prefixo — timestamp, UUID, ordem de dicionário.

ETAPA 02

Promotores: seis lentes, e o trabalho delas é cobertura

Seis prompts em texto puro, lidos da pasta promotores/ — o código lê a pasta, não importa nada dela. Cada um olha o mesmo diff sob uma lente diferente e devolve um array JSON de acusações. Essa lista ninguém vê: acusar é barato.

vazamento_contexto.mdvazamento_de_contextoseguranca_iadado de um usuário aparecendo para outro; filtro de tenant ausente

Como a mensagem de cada promotor é montada

[ diff do PR ]                 ← prefixo grande, IGUAL nos 6, com cache_control
[ bloco de orçamento ]         ← derivado do diff, então idêntico nos 6
[ contexto do repositório ]    ← opcional, também igual nos 6, com cache_control
[ conteúdo do arquivo .md ]    ← a lente, específica de cada promotor

A primeira chamada roda sozinha e as outras cinco depois, em paralelo. Não é estilo: uma entrada de cache só fica legível depois que a primeira resposta começa a chegar — disparando as seis juntas, todas pagam preço cheio pelo diff. Medido: cinco das seis voltavam com cache zero.

O esquema da acusação

JSON, nunca YAML — o Haiku quebra YAML e a acusação some em silêncio. O parse tem try/except e devolve a saída crua no fallback: acusação nunca morre por erro de formato. 

{
  "id": "vazamento_01",
  "categoria": "vazamento_de_contexto",
  "local": "search.py:112",
  "hipotese": "retrieve_docs não filtra por tenant_id",
  "arbitro": {"regra": "quem não é dono não pode ler",
              "onde": "docs/PRD.md:43"},
  "provado_se": "canário do usuário B aparece na resposta do usuário A",
  "confianca": "media"
}
  • arbitro — o objeto acima ou null. Nunca uma sigla solta. Só conta com o campo onde preenchido.
  • provado_se — o advogado já começa sabendo o que procurar, em vez de gastar voltas do laço decidindo.
  • hipotese — uma linha. Prosa longa ancora o advogado e o juiz.
O erro mais caro do projeto

Numa medição em 10 PRs reais, 94 acusações vieram com árbitro preenchido e 93 citavam os critérios de aceite de um desafio — aplicados a repositórios que não tinham nada a ver com ele. Os prompts chumbavam rótulos (AC1, R1, C8) que nunca existiram nem no desafio: foram inventados e o modelo foi mandado citá-los "verbatim".

A regra que isso comprou: regra sem procedência é opinião. Hoje o que o repositório documenta entra por CONTEXTO_REPO, em tempo de execução, e null é a resposta honesta para a maioria dos repositórios do mundo. Um teste (tests/test_prompts_limpos.py) verifica isso mecanicamente — prompt regride em silêncio, asserção não.

Duas coisas que o prompt do promotor não pode fazer

Não pode pedir seletividade. "Reporte apenas problemas relevantes" faz o modelo se autocensurar e engolir achado real. O trabalho dele é cobertura; quem filtra é o advogado, que tem ferramenta — e essa divisão é o produto inteiro.

Não pode chumbar critério de projeto nenhum. Ver o quadro acima.

O orçamento por lente: calibração de escala, não filtro

Medido nos 10 PRs: a contagem de acusações era praticamente constante (de 7 a 29) enquanto o diff variava 400× — 13 acusações para um PR de uma linha. Os promotores não escalam, eles produzem "um punhado". 

orcamento_por_lente(diff) = clamp(1, ceil((3 + linhas) / 6), 10)

   1 linha  → 1 por lente     (antes: 13 no total)   MORDE
  13 linhas → 3 por lente                            não morde
 389 linhas → 10 por lente (teto)                    não morde

A diferença importa: "este diff muda 1 linha; emita até 1" é escala. "Reporte só o relevante" é filtro de qualidade, e é o que faz o modelo engolir achado real. E o anteparo marca, não apaga: quem estourou ganha _excedente_orcamento e vai para o fim da fila.

As fontes externas, em paralelo

veredito/fontes.py :: acusa() · cruza() · _mesmo_ponto()

bandit e semgrep rodam sobre os arquivos do diff, e o resultado encontra a lista dos promotores no cruzamento — que é código, não prompt:

  • Coincide com um promotor (mesmo arquivo, faixa ±2 linhas, região ≤10 linhas) → corrobora: não gasta vaga, e o parecer cita a ferramenta verbatim.
  • Ninguém viu → entra como acusação nova.
  • O arbitro do scanner é sempre null: a regra é da ferramenta, não do repositório revisado.

Em paralelo, nunca em série. Mostrar o achado do scanner ao promotor ancora a lente — dizer que a linha 31 "já está coberta" convida a ler "esse arquivo já está coberto" — e destrói o sinal de corroboração, que só vale entre fontes independentes. O teto é baixo: 2 ou 3 achados contra 45 dos promotores. É corroboração, não motor.

ETAPA 03

Seleção: quem ganha uma vaga no laço caro

Cada acusação verificada custa dinheiro e tempo. Esta etapa decide quem passa — e, tão importante quanto, registra quem não passou e por quê.

veredito/promotores.py :: seleciona_com_escopo() · deduplica() · consenso() · escopo()

Primeiro, a deduplicação

Funde acusações que apontam o mesmo local e o mesmo árbitro, e faz isso antes do advogado: deduplicar só no parecer limpa o texto com o dinheiro já gasto. É conservador de propósito — sem árbitro ou sem local, não funde. Fundir dois achados distintos é pior que gastar uma vaga a mais.

A sobrevivente é a de maior confiança; as outras viram _duplicatas. E existe um campo que separa dois casos que parecem iguais e não são: _corroborado=True significa que promotores diferentes chegaram ao mesmo ponto — isso é sinal. False significa que o mesmo promotor se repetiu — isso é redundância interna, e apresentar como "N lentes independentes apontaram" seria falso.

Esta chave é rígida de propósito — medido em 606 acusações

A fusão do parecer (etapa 05) usa uma chave mais frouxa e funciona. A pergunta óbvia era se ela poderia substituir esta também. Sobre 606 acusações de 27 rodadas em disco, custo zero de API: a chave atual funde 11, a da apresentação funde 88. Parece vitória — e é o padrão dos "45% de árbitro" outra vez, o número subindo porque mede outra coisa. Lidos à mão, cerca de metade dos grupos novos funde defeitos genuinamente distintos. O pior caso juntava "o limite nunca é verificado" (bug funcional real) com dois achados de estilo, mesma linha, mesma regra citada.

A mesma chave é segura para apresentar e perigosa para selecionar. No parecer, uma fusão errada não esconde nada — as hipóteses e as provas seguem no bloco. Na seleção, o fundido nunca é verificado.

E afrouxar aqui não economizaria API: TOP_N é teto duro, então a vaga que o dedup libera é preenchida pela próxima da fila e a rodada custa o mesmo. O que compraria é cobertura — o mesmo dinheiro verificando suspeitas mais distintas.

As três primeiras camadas despriorizam, não descartam: o excedente vai para o fim da fila e ainda entra se sobrar orçamento. Teto duro sumiria com acusação sem ninguém ver, e "nada é descartado em silêncio" vale para o arquivo que fica, não só para o console que rola.

O consenso ordena, e nunca julga

consenso() conta quantas lentes distintas apontaram o mesmo ponto (mesmo arquivo, faixas que se tocam com folga de 2 linhas). Medido em quatro rodadas com gabarito: nos PRs com defeito, 5 ou 6 lentes convergem no mesmo ponto; no PR limpo, nunca passa de 2 — apesar de o PR limpo ter mais acusações brutas. Não é volume, é convergência.

E ele decide só a ordem

O advogado nunca vê esse número. Se visse, cinco lentes concordando viraria pressão para confirmar, e o produto passaria a medir opinião de modelo em vez de exit code. A severidade também não muda: ela segue a força da prova, e cinco lentes concordando não são prova de nada. Dois testes travam isso.

Honestidade sobre o que ele não faz: a hipótese era que o consenso consertaria a seleção. O contrafactual sobre dados reais deu nenhuma mudança nas vagas. O que fez o defeito ser julgado foi orçamento, não ordem — então o campo ficou como sinal auditável, e não como melhoria que a medição não sustenta.

O escopo, gravado antes do laço

escopo() produz o retrato do que a rodada olhou e do que ela levantou e não olhou, com a conta fechando: levantadas = fundidas + testadas + não testadas. Cada uma que ficou de fora carrega a posição na fila e o motivo — e o motivo é escrito do ponto de vista de quem ficou de fora, não da camada que a moveu ("abaixo do corte do teto", nunca "ganhou vaga de cota").

E as fundidas saem com hipótese, não como contagem. Até 18/08 a acusação que não coube no orçamento aparecia inteira no parecer — categoria, local, hipótese, posição — e a fundida aparecia como (Outras 3 eram duplicatas.). Ou seja: a que o dedup engoliu por engano ficava menos visível que a que simplesmente não coube, e o engano é o caso grave dos dois. Enquanto a chave for heurística, essa lista é a única defesa que a etapa tem: o autor do PR lê a hipótese e decide sozinho. A invariante é que a contagem e a lista batem — contagem 3 com lista de 1 seria a métrica medindo outra coisa.

Isso nasceu de um parecer que abria com "3 com parecer, 0 descartados, 0 inconclusivos" numa rodada de 24 suspeitas levantadas. As 21 que não couberam sumiam do arquivo. O console dizia, mas o console rola e o parecer fica.

ETAPA 04

Advogado: a única peça que é agente de verdade

Laço: pensa → ferramenta → resultado → decide. Ele vê uma acusação por vez, isolado — sem histórico compartilhado, para que uma acusação fraca não contamine a próxima e para que o prefixo do diff fique idêntico em todas as chamadas.

veredito/advogado.py :: julga() · _sistema() · _parse_veredicto() · _consolida_ferramentas()

Ele não argumenta, não opina e não avalia plausibilidade. Ele testa. Prova é um artefato que outra pessoa possa rodar e ver o mesmo resultado — nada mais.

Como a chamada é armada

runner = cliente.beta.messages.tool_runner(
    model            = claude-opus-5,
    max_tokens       = 64000,          # cobre raciocínio + resposta SOMADOS
    max_iterations   = 10,             # teto do SDK
    stream           = True,           # obrigatório com max_tokens alto
    thinking         = {"type": "adaptive"},
    output_config    = {"effort": "high",
                        "task_budget": {"type": "tokens", "total": 30000}},
    betas            = ["task-budgets-...", "server-side-fallback-..."],
    fallbacks        = "default",      # recusa do classificador não derruba a rodada
    system           = [SISTEMA com cache_control],
    tools            = [prova_diferencial, run_tests, read_file, grep, http_request],
    messages         = [ diff · arquivos do PR (cache_control) · a acusação ],
)
  • Duas travas para o laço, de propósito: o max_iterations do SDK e um break no for. Uma das duas já falhou em teste.
  • Timeout por acusação: 180 s.
  • stop_reason antes de content, sempre. Uma recusa do classificador de cibersegurança vem como HTTP 200 com content vazio — ler content[0].text vira IndexError no meio da rodada.

Bateu no teto? O fechamento forçado

Estourar as voltas não pode custar a perícia inteira. Uma chamada final sem ferramentas (tool_choice: none, effort: low) obriga o advogado a concluir a partir do que já descobriu — e, se não descobriu nada, a dizer INCONCLUSIVO com o que tentou, que é exatamente o texto de que o parecer precisa.

A contagem que alimenta o juiz

Cada chamada de ferramenta registra o próprio desfecho — não é o texto de retorno que é farejado depois. Três contadores saem daqui, e a distinção entre os dois últimos foi uma decisão cara:

ContadorSignificaEfeito no juiz
ferramentas_oka ferramenta respondeué observação — sustenta veredito
ferramentas_erroexistia, foi tentada, não respondeuconverte para inconclusivo (R3)
ferramentas_indisponivelo projeto revisado não a declarounão converte — mas nunca contou como sucesso

Uma dica de prompt que vale por uma feature

A prova diferencial só assina PROVADO se o teste passa no base e falha no head — o que parece impedir provar defeito em endpoint novo (que dá 404 no base por ausência, não por defeito). A saída é escrever o teste sobre a invariante, não sobre o endpoint: 

ruim: "GET /shared/1 como carol devolve 200"     → 404 no base, inconclusivo
bom:  "carol não alcança o documento de alice
       por nenhuma rota"                        → passa no base (não havia como
                                                  vazar), falha no head. PROVADO.

A invariante quase sempre já vale no commit base — é por isso que ela é invariante.

Expansão guiada por área cega

Terminado o laço, o orquestrador pergunta se vale gastar mais. O gatilho não é taxa de acerto ("7 de 8 provaram, deve haver mais") — num PR real, oito acusações eram o mesmo defeito visto por cinco lentes, e expandir assim gastaria reprovando o que já se sabe. O gatilho é ausência de exame: um ponto que três ou mais lentes viram e que nenhuma acusação julgada tocou.

promotores.aglomerados_nao_examinados() · EXPANSAO_MAX=3 · EXPANSAO_MIN_LENTES=3

O efeito no banco, medido e dito

Um retrato do banco é tirado antes do laço e outro depois. O delta vai para efeito_no_banco.json e para o parecer. Três desfechos, e eles não podem usar a mesma frase:

Guarda que morre de excesso morre igual

Antes, sem banco declarado o retrato falhava e todo PR de terceiro fechava com "a rodada pode ter criado ou removido linhas" — falso, porque ali nenhuma ferramenta alcança banco. Alarme que dispara sempre ensina o leitor a pular justamente a linha que existe para o caso raro. E, antes disso, seis rodadas gravaram "limpo": true sem terem conseguido conectar: a falha de medição usava a mesma frase do sucesso.

FERRAMENTAS

As cinco ferramentas do advogado

Declaradas com @beta_tool — a docstring é literalmente a descrição que o modelo lê. Todas moram em veredito/ferramentas.py, que tem uma regra arquitetural: zero chamada de LLM ali dentro. É isso que faz a perícia inteira ser conferível com pytest.

prova_diferencial(codigo_do_teste, nome_do_arquivo)
a única que assina PROVADOexecuta código

Escreve um teste pytest nos dois worktrees, roda dentro do container e compara. Provado significa uma coisa só: o teste passa no commit base e falha no head. Qualquer outra combinação não é prova.

Antes de tocar em disco, recusa duas coisas: projeto que não declara o bloco codigo no veredito.yml (marcado indisponível, não erro) e código de teste com DROP/DELETE.

Quem seria condenado passa por uma confirmação: o base roda de novo, depois do head. Custa ~7 s e mata dois falsos positivos — teste não determinístico e poluição de estado, já que o head sempre roda por último.

artefato: artefatos/prova_<id>.json + o teste escrito

http_request(metodo, caminho, corpo, como_usuario)
sustenta severidade altafala com o app real

Chama a API do app rodando, autenticado como uma das contas declaradas no veredito.yml. Prova alcance: dá para fazer isso de fora, agora — o que vale mais que causalidade, e é a única via que sustenta severidade alta junto com o árbitro.

As contas existem para testar isolamento: é preciso pelo menos três, e uma tem que ser dona de nada — o controle negativo. Qualquer dado de outro usuário que apareça para ela é vazamento, sem precisar interpretar.

Detecta sozinho quando o LLM do app alvo está dublê e registra isso por acusação, para o juiz aplicar a regra R4 mecanicamente depois.

artefato: artefatos/http_<id>.json

read_file(caminho)
essencial

Lê um arquivo do código sob revisão (o worktree do head), com número de linha. Tolera raiz errada: os promotores discordam entre si sobre onde a árvore começa, então o caminho é resolvido por sufixo plausível em vez de exigir acerto exato.

O prompt do advogado diz explicitamente para não usá-la nos arquivos do PR — eles já vieram no bloco cacheado, e a resposta seria idêntica com uma volta gasta.

grep(padrao, glob)
essencial

Regex sobre o código sob revisão, devolvendo arquivo:linha: conteúdo, com teto de resultados. É com read_file a dupla mínima: sem elas não há observação, e o pré-voo aborta.

run_tests(expressao)
recusa quando não sabe

Roda a suíte já existente contra o código do PR — serve para ver se a mudança quebrou o que já era testado, não para provar acusação nova.

Sem codigo declarado no veredito.yml, ela recusa dizendo: rodar a suíte inteira do repositório de um desconhecido dentro do container é exatamente o que apagou um banco em 11/08.

A tabela-verdade da prova diferencial

Esta é a regra central em código, e o LLM não participa da decisão. ferramentas._classifica():

Por que a terceira coluna existe

O docker compose devolve 1 quando o daemon falha — o mesmo código de "teste falhou". Sem conferir que a saída tem linha de resumo do pytest, um soluço do Docker entre as duas execuções vira acusação crítica falsa.

ETAPA 05

Juiz: as regras que não podem ser opinião

Lê tudo do disco, aplica sete regras determinísticas sobre cada veredicto, agrupa os achados que são o mesmo defeito e escreve o parecer. Roda em milissegundos, sem rede, e tem teste — ajustar o formato pela trigésima vez não pode re-executar o advogado.

veredito/juiz.py :: sentencia() → carrega_do_disco() → organiza() → aplica_regras() → formata_parecer()

As regras, na ordem em que rodam

Os nomes (R0…R4) são históricos e não são a ordem de execução. Esta é a ordem real:

#RegraO que fazNasceu de
R0 o artefato manda advogado disse PROVADO e o exit code disse outra coisa? vale o exit code sem ela, "o LLM não sobrescreve o veredito" é só intenção
R0b prova ponta a ponta é fato do artefato prova_ponta_a_ponta só é verdadeira se o artefato HTTP registra que a chamada alcançou a API morava dentro de if artefato is not None — e ficava muda justo na via que sustenta severidade alta
R4 LLM do app alvo dublê REFUTADO em categoria que depende do modelo → INCONCLUSIVO sem chave de API, o app responde a mesma coisa para qualquer pergunta — "não obedeceu" viraria absolvição falsa
R3b zero observação não é veredito PROVADO ou REFUTADO com nenhuma ferramenta bem-sucedida → INCONCLUSIVO, com a causa com a worktree corrompida, o advogado disse PROVADO duas vezes escrevendo no próprio motivo que as ferramentas falharam
R3 execução falhou artefato com erro → INCONCLUSIVO, nunca absolvido e lê só erro: ferramenta que o projeto não declarou não converte
R1 CRÍTICA exige autoridade que não seja o modelo duas vias, qualquer uma basta: árbitro com procedência ou prova ponta a ponta o mesmo SQL injection saiu CRÍTICA por uma lente e SUSPEITA por outra — a severidade seguiu o acaso, não a prova
R2 teto sem ponta a ponta prova que não é ponta a ponta → severidade no máximo MEDIA é o que limita todo PR de terceiro sem veredito.yml

Todo rebaixamento fica registrado em regras_aplicadas. Parecer que rebaixa sem dizer por quê é tão opaco quanto um que não rebaixa.

A distinção mais delicada do projeto

Guarda que não consegue olhar tem que dizer que não olhou — e isso é diferente de olhar e não achar nada. A R3 tratava as duas iguais. Numa revisão de PR de terceiro, cinco refutações obtidas por leitura (com o grep funcionando) viraram quatro inconclusivos, porque o advogado tinha tentado uma ferramenta que aquele projeto não tem. E a que sobrou sobreviveu por acaso: naquela ele não chegou a tentar. Mesma prova, desfecho decidido por qual ferramenta o modelo chamou.

Hoje: erro converte, indisponivel não. Mas indisponível nunca passou a contar como observação — refutar a partir do diff que já veio no prompt, sem abrir o repositório, é argumentar, e a R3b continua disparando.

A fusão: três achados que são um defeito viram um

veredito/fusao.py :: agrupa() · chave() · procedencia()

Duas rodadas reais publicaram três achados no comentário do PR, e os três eram o mesmo defeito, com o mesmo conserto. A deduplicação anterior não pegava porque os dois campos da chave oscilam: 

local :  103   ·   104   ·   103-106
onde  :  "REGRAS.md:Acesso e isolamento"
         "REGRAS.md (Acesso e isolamento)"
         "REGRAS.md - Acesso e isolamento"
         "REGRAS.md:Acesso e isolamento (linhas ~13-14)"

Cada par acertava um eixo e errava o outro. A chave estava certa no espírito e rígida na letra. O conserto veio de uma pergunta que virou princípio:

A procedência é fato do repositório; a paráfrase da regra e do conserto é opinião do modelo. A chave se constrói do fato.

Então funde por (arquivo do código, arquivo da regra, seção da regra), com a linha entrando por proximidade e não por igualdade. Sem árbitro, não funde — há contraexemplo medido em que quatro acusações na mesma linha eram quatro preocupações diferentes. E fundir é seguro aqui, na apresentação: antes do advogado, uma fusão errada custaria uma vaga de verificação.

E depois a fusão vira exit code, também

veredito/prova_de_fusao.py + orquestrador._prova_as_fusoes() — ligado em 18/08, verificado em produção em 19/08

O agrupamento acima decide "é o mesmo defeito?" por semelhança de endereço e procedência. Funciona — mas era o único lugar do pipeline que argumentava em vez de testar, num produto cuja tese é o contrário. Depois do advogado existe artefato executável, então a pergunta vira medição: 

reverte UM trecho do diff  →  quais testes param de falhar?

  todos param       → um trecho explica todos: É O MESMO DEFEITO
  só alguns param   → aquele trecho explica só aqueles: SÃO DEFEITOS DIFERENTES
  nenhum, ou não deu para medir → INCONCLUSIVO, e diz por quê

O terceiro estado não é decoração: sem ele, "não consegui medir" viraria "são o mesmo", que é a absolvição falsa de sempre com roupa nova. E a prova faz o que a heurística não consegue: separar. Se o trecho que conserta A não conserta B, os dois voltam a ser dois achados — com evidência de que são dois, e a contagem do comentário acompanha.

A granularidade é trecho, nunca hunk

O PR medido é um hunk só com duas mudanças dentro — uma docstring e a condição de autorização. Revertê-lo inteiro faz tudo passar, mas isso é só "reverter o PR conserta o PR": trivialmente verdade, e não diz nada. O que deu sentido ao experimento foi separar as duas — revertendo só a docstring os três testes continuaram falhando (controle negativo), e revertendo só a condição os três passaram. Por isso a unidade é o trecho contíguo de linhas alteradas (os opcodes do difflib), e diff com um trecho só é INCONCLUSIVO, nunca "provado". Teto de 12 trechos por grupo, porque cada um é uma rodada de pytest.

Quem mede e quem lê

A medição roda no orquestrador, depois do laço caro, e grava fusao.json. O juiz e o comentário apenas leem esse arquivo. A divisão é a disciplina nº 2 do projeto: sem ela, reajustar o parecer passaria a subir container, e a propriedade de o juiz rodar em milissegundos sem rede morreria em troca de nada.

SituaçãoO que o bloco do parecer diz
MESMO_DEFEITO"FUSÃO PROVADA: revertendo um único trecho do diff, os N testes param de falhar. A causa é a mesma — medido por exit code, não inferido por semelhança."
DEFEITOS_DIFERENTES"FUSÃO DESFEITA POR PROVA: o trecho que conserta X não conserta Y. São causas diferentes, apesar de caírem no mesmo lugar."
INCONCLUSIVO
ou arquivo ausente		"AGRUPAMENTO NÃO PROVADO (<causa>). Os N achados foram agrupados por endereço e procedência, que é indício e não prova."

Sem fusao.json — rodada sem Docker, projeto sem bloco codigo, rodada antiga — o parecer sai idêntico fora de uma linha, e a linha que muda é exatamente a que diz se o agrupamento foi provado ou inferido. O teste que mais importa é o da ausência: sem ele, uma rodada sem container publicaria "FUSÃO PROVADA" sem nada ter rodado.

O limite, dito em voz alta

A bissecção exige prova diferencial de todos os membros do grupo: ela precisa de um teste para reexecutar contra o código alterado. Achado provado só por http_request sustenta o achado (a R1 tem duas vias) mas não deixa esse objeto — e aí o grupo inteiro sai INCONCLUSIVO com essa causa. Medido em 19/08 num PR real: dos três condenados, só um tinha artefato de prova diferencial.

A variação nova do padrão de bug — 19/08

A prova de fusão nunca tinha executado em produção, e o try/except que degradava honestamente ("o agrupamento fica por heurística") era exatamente o que escondia isso. Dois bugs, a mesma família: um import que nunca foi adicionado, e _por_id("prova_{}.json") — onde _por_id faz glob e {} é literal. O segundo é o pior: sozinho, teria produzido um produto que diz "não consegui medir" em toda rodada, para sempre, parecendo que rodou.

E os testes escritos no dia anterior não pegaram nenhum dos dois — os dois evitavam o caminho feliz por construção. A primeira versão do teste novo também não pegava, porque o valor esperado era igual ao valor errado: teste cujo resultado esperado coincide com o do defeito não discrimina nada.

O formato do parecer

[SEVERIDADE] [CONFIANÇA] Categoria — arquivo:linha
O QUE: uma frase.
ÁRBITRO: <a regra (arquivo:linha)>   ou   "nenhum citado"
EVIDÊNCIA: <artefato: teste que falha base→head / chamadas HTTP>
           ou: o que foi tentado e por que não fechou
CONSERTO SUGERIDO: uma frase.        ← só para condenados

E o parecer inteiro tem cinco seções, nesta ordem:

  1. Cabeçalho de escopo — "N suspeitas levantadas, M testadas dentro do orçamento (TOP_N=M)".
  2. CONDENADOS — um bloco por defeito, não por veredicto.
  3. DESCARTADOS, COM MOTIVO.
  4. INCONCLUSIVOS, COM CAUSA.
  5. LEVANTADAS E NÃO TESTADAS — na ordem em que a fila as alcançaria com um teto maior, cada uma com posição e motivo. E, junto, as fundidas como duplicata, cada uma com a hipótese e em qual acusação foi fundida.
  6. EFEITO NO BANCO DO APP — só aparece quando há o que dizer.
A moldura decide como isso é lido

Com o mesmo número dos dois lados: "25 levantadas, 8 testadas dentro do orçamento" é escopo declarado; "17 não testadas" é confissão. A primeira é a verdadeira — teto de orçamento é escolha de operação, não falha da perícia. As duas listas do meio (descartados e inconclusivos) são a peça que quase nenhum concorrente tem, e precisam ser enquadradas em voz alta, senão soam como erro admitido.

ETAPA 06

Entrega: o parecer chega ao PR

veredito/comentario.py :: monta() · do_disco() · corta() — e posta_parecer.py

O comentário é montado do disco, com a mesma disciplina do juiz: ajustar o formato pela trigésima vez não pode gastar API.

  • Condenados abertos, por extenso — é o que o autor precisa agir.
  • Descartados e inconclusivos em <details> — presentes, nunca omitidos, mas sem competir com o achado.
  • A contagem é de defeitos, e não de veredictos: fusao.agrupa agrupa por heurística e prova_de_fusao.aplica refina com o que a bissecção mediu — inclusive desfazendo grupo, e a contagem acompanha.
  • Corta com folga para o rodapé, porque o comentário do GitHub tem teto de tamanho.

Atualiza, nunca empilha

O corpo começa com a marca <!-- veredito:parecer -->. Antes de postar, o script procura um comentário nosso com essa marca e faz PATCH nele. Sem isso, uma Action que roda a cada push deixaria doze comentários num PR de três dias — e bot assim é bot que o time desliga na primeira semana.

Dry-run é o padrão

posta_parecer.py só imprime; postar de verdade exige --postar. Comentar num PR é público e irreversível na prática: a notificação sai para todo mundo que segue o repositório no mesmo segundo, e apagar depois não desfaz o email. Efeito irreversível se pergunta antes.

E a conferência de que funcionou é a API do GitHub (contar os comentários do PR), não a linha que o script imprimiu — criado:/atualizado: é autodeclaração do código sob teste, que é a mesma distinção da regra R0.

Por que Action e não bot hospedado

O produto precisa rodar o app do cliente. Um bot hospedado exigiria clonar o código e subir o stack de cada cliente em infra de terceiro — e o comprador que mais precisa é justamente quem não deixa o código sair. A CI do cliente já faz checkout de base e head, já sobe o app, já roda testes: a Action inverte a restrição em vantagem.

O rastro da rodada sobe como artefato da Action sempre, inclusive quando a rodada falha — que é quando ele mais vale.

RISCO

O agente pode destruir o que ele testa

É a classe de risco mais séria do produto, e não é bug pontual: é consequência direta do desenho. Aconteceu três vezes, cada uma com uma cara diferente.

Caso 1 · o payload

Um promotor pediu prova com email="admin'; DROP TABLE users--", e o advogado tem http_request apontado para o app rodando. O classificador de cibersegurança recusou e estava protegendo — tratar a recusa como obstáculo teria consertado a coisa errada. Injeção se prova por leitura: ' OR '1'='1 devolvendo linhas demais.

Caso 2 · a suíte do base

A prova diferencial roda a suíte do repositório nos dois commits. O commit base era anterior ao conserto do próprio autor ("stop the test suite from wiping the app database") e apagou o banco. O desenho trata o base como referência inerte — e rodar código não é inerte.

Caso 3 · a regra impossível

Numa rodada real, uma tabela saiu de 0 para 3 linhas. Nada destruído, mas provar injeção na rota de compartilhamento exige chamar a rota que compartilha. "Prove de forma que só lê" era regra que o desenho viola por construção — e regra impossível no mesmo prompt ensina que as regras dali são aproximadas.

E o diagnóstico óbvio estava errado

Procurar DROP no diff não pega nada: o DROP SCHEMA existia igual nos dois commits. O que o PR mudou foi para onde ele aponta. O perigo estava no código que a mudança não tocou.

O princípio: contenção, não predição

Adivinhar o que o código faz perdeu as duas vezes. O que funciona é impor a fronteira de fora. A linha certa também mudou: não é entre ler e escrever, é entre criar e destruir.

  • 🚫 o payload injetado é sempre read-only — DROP, DELETE, UPDATE, INSERT proibidos;
  • ✅ a chamada a um endpoint documentado pode criar registro, quando o defeito mora nele;
  • 🚫 em qualquer via: apagar ou modificar o que já existia.
CamadaMecanismoOnde

Por que só o base: a CI do cliente roda o head a cada push, então o risco marginal ali é zero. O base ninguém roda mais — é lá que o risco é só nosso. A escotilha (PERMITIR_REDE_NO_BASE=1) existe desligada: se o arnês de teste precisa de internet, o base vira inconclusivo rotulado, dizendo que foi o isolamento e não o PR.

O vão que ainda existe, dito em voz alta: a contenção fechou o banco para o http_request; a rede, não. E a contenção do app é desligada por padrão. Quando ligada e o retrato falha, a rodada aborta — contenção pedida e não confirmada é o pior dos mundos.

CONTRATO

O veredito.yml: o projeto se descreve

Até certo ponto da história, as contas de teste estavam escritas dentro do código — e era isso que fazia metade do produto só funcionar num repositório. Hoje o que é do projeto revisado mora num arquivo na raiz dele, como um Dockerfile.

ArquivoDescreveMuda por
veredito.ymlo projeto revisado: como sobe, como autentica, layout do código, onde é seguro escrevercliente
.envcomo nós operamos: modelo, orçamento, TOP_N, timeoutsnunca

Precedência: variável de ambiente > veredito.yml > padrão do código.

O que ele declara

app:      compose · api · web · saude · subir · espera_s · preparar
codigo:   montagens · trabalho · testes · testes_no_repo · banco_de_teste_semeado
auth:     rota · campo_usuario · campo_senha · campo_token
banco:    servico · usuario · senha · nome · descartavel_testes · descartavel_app
contas:   nome · email · senha · possui        # ≥3, e uma com possui: 0
contexto: caminho para o que o repositório documenta sobre si mesmo

Ausente não é vazio, e errado não é ausente

  • Sem arquivo → a rodada acontece com leitura e grep, e o pré-voo diz o que perdeu. Ausência é limite honesto de um projeto que não se descreveu.
  • Arquivo errado → levanta (conta sem senha, nomes repetidos, contas: []). Engano do operador seguido com metade do arquivo produz rodada que parece boa e não é.
Por que as contas vêm de fora

A prova ponta a ponta — a única via que sustenta CRÍTICA junto com o árbitro — dependia de quatro emails escritos no nosso repositório. E são necessárias três contas no mínimo porque "qualquer coisa envolvendo o acesso de um usuário aos dados de outro precisa de pelo menos três contas para ser testada direito": uma dona, uma destinatária e uma que não deveria ver nada. A terceira, com possui: 0, é deduzida como controle negativo — declarar duas vezes é convidar as duas a divergirem.

O padrão de bug que este projeto produz

A guarda existe, mas está condicionada ao mesmo sinal que ela deveria vigiar — então fica muda exatamente onde é necessária. Aconteceu uma dúzia de vezes, sempre com cara diferente. As perguntas que acham isso:

  • Toda guarda dentro de um if: o que acontece quando a condição é falsa?
  • Toda guarda que alarma: ela consegue ficar quieta? Guarda que dispara sempre morre de excesso.
  • Todo try/except que degrada honestamente: ele consegue distinguir "degradei" de "nunca executei"? Foi o que escondeu a prova de fusão por um dia inteiro.
  • Todo teste: o valor esperado é diferente do valor que o defeito produz? Se coincidirem, ele não discrimina nada.
  • Dá para provar em vez de inferir? Foi a pergunta que transformou "é o mesmo defeito?" em exit code.
  • Toda métrica: isto pode estar medindo outra coisa? (94 árbitros "preenchidos" estavam preenchidos com lixo reciclado.)
  • Toda chave derivada de um campo: e se o campo sumir? E ela é feita de fato ou de paráfrase?
  • Todo or <valor padrão>: consertar o valor trata o sintoma — o mecanismo é o fallback existir.
  • E toda guarda precisa ser vista falhando, com a violação injetada. Guarda confiada é decoração.

OPERAÇÃO

Como rodar

Revisar um PR do GitHub

py -3.12 revisa_pr.py https://github.com/dono/repo/pull/123
py -3.12 revisa_pr.py <url> --top-n 5
py -3.12 revisa_pr.py <url> --so-preparar   # monta e não roda: não gasta API

Rodar contra um repositório já em disco

py -3.12 -m veredito.orquestrador
py -3.12 -m veredito.orquestrador --top-n 2
py -3.12 -m veredito.orquestrador --manual        # uma acusação de bancada, exercita o pipeline
py -3.12 -m veredito.orquestrador --reusar        # reusa as acusações da rodada anterior
py -3.12 -m veredito.orquestrador --sem-scanner   # só os promotores

Reajustar o parecer sem gastar nada

py -3.12 -m veredito.juiz         # lê a última rodada do disco e reimprime
py -3.12 posta_parecer.py <url>   # dry-run; --postar comenta de verdade

Conferências grátis, em segundos

py -3.12 checar_contencao.py       # as camadas de contenção estão de pé?
py -3.12 -m pytest tests -q        # a suíte do próprio Veredito

Se os promotores deixarem passar

Primeiro descubra onde vazou, imprimindo a lista bruta. Nunca acusou é problema de cobertura; acusou e não entrou no TOP_N é problema de ranking. O conserto é diferente. Depois, a escada do mais barato ao mais caro:

  1. Contexto — promotor de PRD sem PRD não acha nada, com qualquer prompt.
  2. Dividir o promotor — foi assim que "segurança de IA" virou injection + vazamento.
  3. Pedir volume explicitamente — sem pedir seletividade.
  4. Rodar por arquivo, não por diff inteiro.
  5. Só então trocar de modelo.

A régua: se trocássemos o PR por outro, o agente teria que continuar funcionando. Toda melhoria precisa sobreviver a essa troca.

GLOSSÁRIO

Vocabulário da casa

TermoO que é
AcusaçãoA saída de um promotor: uma hipótese de defeito, com local, árbitro e o que a provaria. Barata, e ninguém a lê fora do sistema.
VeredictoA saída do advogado para uma acusação: PROVADO, REFUTADO ou INCONCLUSIVO, com contagem de ferramentas e uso de tokens.
ArtefatoO arquivo que outra pessoa consegue rodar: o teste diferencial com os dois exit codes, ou o registro das chamadas HTTP.
ÁrbitroA regra violada e onde ela está escrita naquele repositório. Sem o "onde", é null — e null é a resposta honesta na maioria dos repositórios.
Prova diferencialProva de causalidade: passa no base, falha no head. Foi esta mudança que quebrou.
Prova ponta a pontaProva de alcance: a falha acontece de fora, contra o app rodando. Vale mais, e é a única que sustenta severidade alta sem árbitro.
Prova de fusãoA bissecção que responde "estes achados são o mesmo defeito?" revertendo um trecho do diff e olhando quais testes param de falhar. Roda no orquestrador, grava fusao.json, e sem ela o parecer diz que agrupou por indício.
DublêO LLM do app alvo sem chave, respondendo a mesma coisa para qualquer pergunta. "Não obedeceu" ali não é resistência, é ausência de observação.
Controle negativoA conta que não possui nada. Qualquer dado alheio que apareça para ela é vazamento, sem interpretação.
Bucket / cotaO agrupamento de categorias que garante vaga a cada lente no orçamento da rodada.
RodadaUma execução completa, com pasta própria, carimbo de data e commit, e rastro suficiente para ser reaberta depois.
Os princípios, se você for mexer no código

1 · Formato da saída primeiro — sabendo a cara da saída, o agente se desenha. 2 · Pipeline inteiro rodando cedo, mesmo burro, antes de refinar peça. 3 · Uma ferramenta boa vale mais que quatro pela metade. 4 · Demoável > sofisticado e invisível. 5 · Log de tudo: o rastro responde auditabilidade, custo e latência de uma vez. 6 · Medir antes de comemorar — toda métrica nova merece a pergunta "isto pode estar medindo outra coisa?"
